# Hosting Safeer on Render at safeer.mohbaba.online

`render.yaml` defines one Node web service and one Render PostgreSQL database. `scripts/production.mjs` starts it. On every start it applies migrations as the database owner, keeps the limited `safeer_app` runtime role, and serves the web app on `PORT`. The API stays on the service's loopback.

## First deploy

1. In Render choose **New > Blueprint** and pick the Safeer GitHub repository.
2. When asked, set `SAFEER_OWNER_LOGIN` to the email of the first owner account. `SAFEER_APP_DB_PASSWORD` is generated by Render, and `DATABASE_URL` comes from the database.
3. After the first deploy, open the service **Logs** once to read the owner's temporary password. Sign in at `/staff` and change it straight away.
4. In the service **Settings > Custom Domains**, add `safeer.mohbaba.online`. Then, at the DNS provider for mohbaba.online, add a `CNAME` record named `safeer` pointing to the `*.onrender.com` address Render shows. Render issues the HTTPS certificate.
5. Check `https://safeer.mohbaba.online/privacy` and `/api/v1/health`.

## Notes

- The site answers only on `SAFEER_PUBLIC_ORIGIN`. Requests that reach it through the `onrender.com` address get 403, except the health check.
- Cookies are `Secure`, and HSTS is sent. Sign-in and public booking limits use the visitor address: the last `X-Forwarded-For` entry that Render's proxy adds, or Cloudflare's `CF-Connecting-IP` when that last entry is one of Cloudflare's published ranges (the site is behind Cloudflare). If Cloudflare publishes new ranges, update the list in `server.mjs` (D72).
- `npm run check:live` makes read-only requests to the live site: health, pages and security headers, the update notice data, the APK download links, and which commit the deployed files match. It signs in nowhere and changes nothing.
- `npm run test:production` runs `scripts/production.mjs` locally against a disposable database owned by a non-superuser, like Render, before a deploy.
- Back up the database from the Render dashboard. Starter plans keep limited point-in-time recovery, so check yours.
- Migrations only move forward. Never edit an applied migration.
- Pushing to GitHub triggers a Render deploy only when auto-deploy is on. Check the deploy status in Render.

## Google sign-in for passengers (D70, D75)

Passenger accounts are optional. Without these two keys the Profile page says Google sign-in is not available yet, and guest booking is unchanged.

1. In Google Cloud Console (console.cloud.google.com), create or pick a project for Safeer.
2. Google Auth Platform > Branding: app name `Safeer`, a user support email, the logo (a 120x120 PNG of the D76 Route Pin mark, under 1 MB), application home page `https://safeer.mohbaba.online/`, privacy policy `https://safeer.mohbaba.online/privacy`, authorized domain `mohbaba.online`, and a developer contact email.
3. Audience: External, then publish the app. Safeer asks only for `openid email profile`, which Google treats as non-sensitive.
4. Clients > Create client > Web application. Authorized redirect URI, exactly: `https://safeer.mohbaba.online/api/v1/passenger/google/callback`. No JavaScript origin is needed. Copy the client ID and the client secret; the secret is shown only once.
5. In Render, open the Safeer web service > Environment, set `SAFEER_GOOGLE_CLIENT_ID` and `SAFEER_GOOGLE_CLIENT_SECRET`, and save so it redeploys. Never put the secret in Git, chat or logs.
6. In Google Search Console, add the domain `mohbaba.online`, add the TXT record it shows in Namecheap (Domain List > mohbaba.online > Advanced DNS), and verify. Use a Google account that owns the Cloud project.
7. Back in Google Auth Platform, choose Verify branding. Until Google approves it, the sign-in screen shows the site address instead of the Safeer name and logo; sign-in itself still works.
8. Run `npm run check:live`: it reports "Google sign-in configured". Then sign in once from Profile on the website, and delete that test account from Profile if you want.

# Hosting on a Namecheap VPS (Ubuntu 24.04)

`deploy/setup-ubuntu.sh` installs Node 24, PostgreSQL 16, Nginx and a Let's Encrypt certificate, and runs Safeer under systemd as the unprivileged `safeer` user.

1. Buy a Namecheap VPS with **Ubuntu 24.04**. Note its IP address and root password.
2. In Namecheap **Domain List > mohbaba.online > Advanced DNS**, add an `A Record`: Host `safeer`, Value = the VPS IP. Remove any `CNAME` for `safeer`.
3. Sign in: `ssh root@<VPS IP>`, then run:

       git clone https://github.com/Baballah2240/Safeer.git /opt/safeer
       OWNER_EMAIL=you@example.com bash /opt/safeer/deploy/setup-ubuntu.sh

4. Read the temporary owner password: `journalctl -u safeer | grep "Temporary password"`. Sign in at `/staff` and change it.
5. To update later, run the same command again. Logs: `journalctl -u safeer -f`.

Secrets live in `/etc/safeer.env` (root only). Back up the database with `sudo -u postgres pg_dump safeer > safeer.sql`. A private repository needs a GitHub deploy key or token for the clone.

## Explicit hosted owner recovery

After verifying a private database backup, open the existing Render service Shell and run the reviewed command from the deployed source:

    npm run identity:recover:hosted -- --email existing@example.com --new-email new@example.com --confirm-reset

DATABASE_URL must be the existing private migration-owner connection, never safeer_app. Omit --new-email to keep the login unchanged. The command prints a generated temporary password once, revokes prior owner sessions, requires password change and audits the action; conflicting emails roll back. Update SAFEER_OWNER_LOGIN separately after a deliberate email change. Do not paste credentials into Git or public logs. Recovery is an operator command, not a forgot-password HTTP bypass.

## Verification before deployment

Run npm run verify:release; it includes every browser workflow. The dedicated repository workflow .github/workflows/postgres16.yml uses an isolated PostgreSQL 16 service. Windows can select a separately provisioned test binary with SAFEER_VERIFY_PG_BIN; persistent runtime/ is never selected automatically. Test summaries do not prove that Render deployed the same commit: compare the deployed login module and build hashes after a successful deployment.
